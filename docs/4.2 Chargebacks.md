# Stage 4.2 — Chargebacks

## 🎯 Objective

After completing the refund generation, I added **chargebacks** to model customer payment disputes.

The goal was to capture another situation where a successful transaction can create financial exposure for the business.

---

## 💡 Why Chargebacks Matter

A refund and a chargeback are different.

- **Refund:** The merchant decides to return money to the customer.
- **Chargeback:** The customer disputes a payment through the payment/banking system.

For FinLeak, chargebacks are important because they can indicate:

- Fraud-related activity
- Customer disputes
- Duplicate payments
- Product/service issues
- Authorization problems

These events will later be useful when analyzing financial leakage and merchant risk.

---

## 🗄️ Database

I created the `chargebacks` table:

```sql
CREATE TABLE chargebacks (
    chargeback_id VARCHAR(30) PRIMARY KEY,
    transaction_id VARCHAR(30) NOT NULL,
    chargeback_timestamp DATETIME NOT NULL,
    chargeback_amount DECIMAL(15,2) NOT NULL,
    chargeback_reason VARCHAR(100),
    chargeback_status VARCHAR(30) NOT NULL,
    FOREIGN KEY (transaction_id) REFERENCES transactions(transaction_id)
);
```

The relationship is:

```text
transactions
      │
      └── chargebacks
```

Each chargeback is linked back to the original transaction using `transaction_id`.

---

## 🧠 Chargeback Generation Logic

I created:

```text
python/generate_chargebacks.py
```

The generation logic was designed as follows:

- Only successful transactions are eligible.
- Target chargeback rate: approximately **1%**
- 90% of chargebacks are for the full transaction amount.
- 10% are partial chargebacks.
- Partial chargebacks are between 50% and 90% of the original transaction amount.
- Chargeback timestamp is between **5 and 45 days** after the original transaction.
- Chargeback status can be:
  - `OPEN`
  - `RESOLVED`

The chargeback reasons are:

```text
FRAUD
CARDHOLDER_DISPUTE
PRODUCT_NOT_RECEIVED
PRODUCT_NOT_AS_DESCRIBED
DUPLICATE_CHARGE
AUTHORIZATION_ISSUE
```

I also used a fixed random seed so that the generated data remains reproducible.

## ⚠️ Modeling Note

One important point I identified during this stage is that:

```text
RESOLVED ≠ necessarily financial loss
```

A resolved chargeback could potentially have different outcomes.

The current dataset only stores:

```text
chargeback_status
```

and does not have a separate field such as:

```text
chargeback_outcome
```

with values such as:

```text
WON
LOST
```

Therefore, I will **not automatically treat every `RESOLVED` chargeback as a financial loss** in later analysis.

This keeps the financial leakage calculations evidence-based instead of making an assumption that the dataset does not support.
