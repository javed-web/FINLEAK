# Stage A — Customers & Merchants 👥🏪

> **Status:** 🔒 Completed & Validated

---

## 💡 What This Stage Is About

Before generating transactions, I needed two basic entities in the FinLeak database:

- Customers
- Merchants

Transactions will later connect these two entities, so getting this layer right was important before moving forward.

I also wanted these tables to contain enough variation to support analysis later.

For example, I don't want every customer to look the same or every merchant to have the same risk profile.

---

# 👤 Customer Dataset

## 🎯 Objective

The customer table represents PayFlow's customer base.

I wanted the dataset to contain enough information to analyze transaction behavior by:

- Customer segment
- Location
- Acquisition channel
- KYC status
- Demographics

The final customer dataset contains:

**100,000 customers**

---

## 🗄️ Customer Table

The table is called:

```text id="1j5z0q"
customers
```

The main fields are:

| Column | Description |
|---|---|
| `customer_id` | Unique customer identifier |
| `customer_age` | Customer age |
| `gender` | Customer gender |
| `city` | Customer city |
| `state` | Customer state |
| `customer_segment` | Customer value segment |
| `acquisition_channel` | How the customer was acquired |
| `kyc_status` | KYC verification status |
| `signup_date` | Customer signup date |

---

## 📊 Customer Segments

I divided customers into three segments:

| Segment | Approx. Share |
|---|---:|
| Mass | 70% |
| Premium | 23% |
| High Value | 7% |

The purpose of having these segments is to make it possible to compare transaction and financial behavior across different customer groups later.

For example, I can eventually investigate whether high-value customers have different:

- Transaction values
- Failure rates
- Refund behavior
- Payment-method preferences

# 🏪 Merchant Dataset

## 🎯 Objective

The merchant table represents businesses accepting payments through PayFlow.

Merchant data is particularly important for FinLeak because several of the future investigations will happen at the merchant level.

For example:

> Are a small number of merchants responsible for a disproportionate amount of refunds or chargebacks?

To support that type of analysis, I generated:

**10,000 merchants**

---

## 🗄️ Merchant Table

The table is called:

```text id="u6j7x1"
merchants
```

The main fields are:

| Column | Description |
|---|---|
| `merchant_id` | Unique merchant identifier |
| `merchant_name` | Merchant name |
| `merchant_category` | Business category |
| `city` | Merchant city |
| `state` | Merchant state |
| `merchant_segment` | Merchant business segment |
| `risk_score` | Merchant risk score |
| `onboarding_date` | Merchant onboarding date |

---

## 🏢 Merchant Segments

Merchants were divided into:

| Segment | Count | Share |
|---|---:|---:|
| SMB | 6,962 | 69.62% |
| Mid-Market | 2,349 | 23.49% |
| Enterprise | 689 | 6.89% |
| **Total** | **10,000** | **100%** |

The distribution is intentionally weighted toward SMB merchants.

This gives us a useful merchant-size dimension for later analysis.

---

## 🛍️ Merchant Categories

The generated merchants belong to categories such as:

- E-commerce
- Travel
- Food
- Gaming
- Utilities
- Education
- Healthcare
- Retail
- Insurance
- Subscription

These categories will become useful later when investigating whether certain types of businesses have different payment or leakage patterns.

---

## 🚨 Merchant Risk Score

Each merchant has a risk score between **5 and 95**.

The normal risk-score distribution was generated around an average of approximately **35**, with variation between merchants.

The purpose isn't to make the risk score itself the answer.

Instead, I want to eventually compare the assigned risk score with actual observed behavior.

For example:

```text id="m3y6r0"
Merchant Risk Score
        ↓
Actual Transaction Behavior
        ↓
Failure / Refund / Chargeback Patterns
        ↓
Investigation
```

This will allow us to ask whether merchants with higher risk scores actually exhibit different transaction patterns.

---

# 🧠 Why I Built This Layer First

The customer and merchant tables form the foundation for the rest of the project.

The transaction table will reference:

```text id="nd1bq4"
transactions.customer_id
        ↓
customers.customer_id

transactions.merchant_id
        ↓
merchants.merchant_id
```

This means every transaction can eventually be analyzed from both sides:

**Customer → Transaction → Merchant**

That relationship will be important for the investigation work later.
