# Stage 7 — Ground-Truth Anomalies

## 🎯 Objective

In this stage, I wanted to verify whether FinLeak could detect a known abnormal event from the payment data.

Rather than randomly searching for an anomaly and assuming that it is meaningful, I used a **known ground-truth scenario** that was intentionally introduced during transaction generation.

The scenario I tested was a payment gateway incident involving `Gateway_A`.

The goal was:

> **Plant a known anomaly → observe the resulting data → verify that the anomaly can be detected.**

---

## 💡 Why I Built This

An anomaly detection system is much more useful if I can test it against something whose behavior I already know.

For FinLeak, I wanted to answer:

> "If a payment gateway actually experiences an incident, can my analytical system identify the abnormal behavior from payment attempts?"

This gives me a measurable detection test instead of simply creating charts and looking for unusual numbers.

---

## 🔍 Existing Ground-Truth Scenario

The project already contained a ground-truth file:

```text
data/ground_truth/transaction_ground_truth.csv
```

I inspected this file before building the validation analysis.

It contained one scenario:

| Field | Value |
|---|---|
| Scenario | `Gateway_A_Incident` |
| Gateway | `Gateway_A` |
| Start | `2026-05-12 23:00:00` |
| End | `2026-05-13 01:00:00` |
| Normal failure rate | 4% |
| Incident failure rate | 10% |

The ground-truth description states that Gateway_A experiences elevated transaction failures during the two-hour incident window.

The ground truth contains one row and has no missing values.

## 🧠 Detection Approach

I then created:

```text
python/validate_gateway_incident.py
```

The script reads the ground-truth scenario and queries the `payment_attempts` table.

I compared:

1. Gateway_A payment attempts during the incident window
2. Gateway_A payment attempts outside the incident window

The key metric was:

```text
Failure Rate =
Failed Attempts / Total Attempts
```

I then calculated:

```text
Absolute Increase =
Incident Failure Rate - Outside Failure Rate
```

and:

```text
Failure Rate Multiplier =
Incident Failure Rate / Outside Failure Rate
```

This gives me both the size of the change and its relative magnitude.

---

## 📊 Observed Results

The actual data showed:

### Incident Period

```text
Gateway: Gateway_A

Total attempts: 1,397
Failed attempts: 296

Failure rate: 21.19%
```

### Outside Incident

```text
Total attempts: 310,374
Failed attempts: 22,368

Failure rate: 7.21%
```

### Anomaly Strength

```text
Absolute increase: 13.98 percentage points
Failure-rate multiplier: 2.94x
```

So Gateway_A's observed failure rate during the incident was almost **three times** its failure rate outside the incident window.

## 🚨 Detection Result

The validation logic successfully classified the event as:

```text
ANOMALY DETECTION RESULT: DETECTED
```

This is important because the system did not simply read an `anomaly = true` column from the transaction data.

Instead, it compared the behavior inside and outside the known incident window.

The evidence was:

```text
Outside incident
7.21% failure rate
        ↓
Incident
21.19% failure rate
        ↓
13.98 percentage-point increase
        ↓
2.94x higher failure rate
        ↓
Anomaly detected
```

---

## ⚠️ Ground Truth vs Observed Data

One important distinction is that the ground-truth file specifies an intended incident failure rate of **10%**.

The observed payment-attempt failure rate was **21.19%**.

I am not treating these two values as contradictory.

The ground truth describes the scenario that was planted during data generation, while the validation analysis measures the actual behavior that ended up in the `payment_attempts` table.

For Stage G, the important test is whether the abnormal behavior is detectable from the resulting data.

It was.

## 💡 What This Adds to FinLeak

This stage gives the project a proper **detection ground truth**.

The workflow is now:

```text
Known incident
      ↓
Payment attempts
      ↓
Measure normal behavior
      ↓
Measure incident behavior
      ↓
Compare
      ↓
Detect anomaly
```

This will become important later when I build the investigation layer.

Instead of asking the AI to invent a reason for an unusual number, I can provide it with measurable evidence such as:

```text
Gateway_A
Failure rate: 21.19%
Baseline: 7.21%
Increase: 13.98 pp
Multiplier: 2.94x
```

The AI can then formulate an investigation hypothesis from that evidence.
