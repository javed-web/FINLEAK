# Stage C — Payment Attempts 🔁💳

> **Status:** 🔒 Completed & Validated

---

## 🎯 Objective

After generating the 1,000,000 transactions, the next question was:

> **What actually happened when a customer tried to make a payment?**

A transaction record only tells me whether the transaction ultimately succeeded or failed.

It doesn't tell me how many times the payment was attempted, which gateway handled each attempt, how long the attempt took, or what response the gateway returned.

That's why I created the `payment_attempts` table.

This table allows FinLeak to analyze:

- Payment retries
- Gateway response behavior
- Failed attempts
- Successful retries
- Processing time
- Attempt-level failure rates
- Gateway performance during specific time periods

---

# 🗄️ Payment Attempts Table

The table is:

```text id="g8xq1s"
payment_attempts
```

Each row represents **one payment attempt**, rather than one transaction.

A transaction can therefore have multiple payment-attempt records.

For example:

```text id="u4p9az"
Transaction TXN001
       │
       ├── Attempt 1 → FAILED
       │
       └── Attempt 2 → SUCCESS
```

This is different from the `transactions` table, where each transaction appears only once.

---

## 📋 Main Fields

The table contains fields such as:

| Column | Description |
|---|---|
| `attempt_id` | Unique attempt identifier |
| `transaction_id` | Transaction associated with the attempt |
| `attempt_number` | Attempt sequence number |
| `gateway` | Gateway used for the attempt |
| `attempt_timestamp` | Timestamp of the attempt |
| `response_code` | Gateway response code |
| `response_message` | Gateway response message |
| `processing_time_ms` | Processing time in milliseconds |
| `attempt_status` | SUCCESS / FAILED |

The `transaction_id` acts as the link back to the main transaction.

---

# 🔁 Retry Logic

The main purpose of this stage was to introduce realistic retry behavior.

Not every transaction should have exactly one attempt.

The final dataset contains:

| Attempts per Transaction | Transactions | Share |
|---|---:|---:|
| 1 | 966,284 | 96.63% |
| 2 | 29,592 | 2.96% |
| 3 | 3,904 | 0.39% |
| 4 | 220 | 0.02% |

This gives the dataset a small but meaningful retry population.

Overall:

**1,000,000 transactions → 1,038,060 payment attempts**

That means there were:

**38,060 additional attempts**

or approximately:

**3.81% retry rate**

# ⏱️ Attempt-Level Information

Each payment attempt also contains:

- An attempt timestamp
- Gateway response code
- Gateway response message
- Processing time
- Attempt status

This is useful because a transaction-level failure rate alone doesn't tell the complete story.

For example, later we could investigate:

```text id="x1tq7n"

   ↓
```

This should give us a more detailed view of payment performance.

# 🚨 Gateway_A Incident

The controlled Gateway_A incident created during the transaction stage was carried into the payment-attempt layer.

The incident window was:

```text id="m8y6kp"
2026-05-12 23:00:00
        ↓
2026-05-13 01:00:00
```

The important part here is that the incident should now be visible at the **attempt level**, where we have much more detailed information about what happened.

I specifically wanted to see whether the failure rate during this window would be significantly different from normal Gateway_A behavior.

---

# 📈 Incident Analysis

I compared Gateway_A payment attempts inside and outside the incident period.

The result was:

| Period | Attempts | Failed Attempts | Failure Rate |
|---|---:|---:|---:|
| Outside Incident | 311,040 | 22,655 | 7.28% |
| Incident | 1,493 | 335 | **22.44%** |

The incident-period failure rate was approximately **3.1×** the rate outside the incident window.

This is an important signal for the later investigation layer.

However, I am deliberately not treating this number as proof of a specific technical root cause.

What the data establishes is:

> Gateway_A experienced a substantially higher payment-attempt failure rate during this two-hour incident window.

The reason behind that increase should be investigated rather than assumed.

# 🐛 Problem Encountered During Generation

The first version of the payment-attempt generator encountered a MySQL error:

```text id="h4f0gk"
mysql.connector.errors.InternalError:
Unread result found
```

The problem occurred because the script was reading transactions using a streaming cursor while attempting to use another cursor/operation on the same MySQL connection.

The connection still had unread rows from the streaming query.

As a result, MySQL Connector/Python prevented the next database operation.

---

# 🔧 How I Fixed It

I changed the implementation to use **two separate MySQL connections**.

Conceptually:

```text id="q0w6de"
Connection 1
    ↓
Read / stream transactions


Connection 2
    ↓
Insert payment attempts
```

This allowed the transaction-reading operation and the payment-attempt insertion operation to proceed independently.

After making this change, the generator completed successfully for all 1,000,000 transactions.

This also made the data-generation process more suitable for the size of the dataset.

# 🧠 Why This Stage Matters

This table adds another level of detail to FinLeak.

Without payment attempts, we could only say:

> "Some transactions failed."

With payment attempts, we can investigate:

> "How many times was the payment attempted?"

> "Did the customer retry?"

> "Which gateway processed the attempt?"

> "Did the gateway fail repeatedly?"

> "Was there a sudden increase in failures during a specific period?"

This makes the later investigation much more interesting.

---

# 🔗 Relationship With the Transaction Layer

The relationship between the two tables is:

```text id="a7q0nd"
transactions
     │
     │ 1
     │
     ▼
payment_attempts
     │
     │ many
     ▼
multiple attempts
```

A single transaction can therefore have:

```text id="h1c8rx"
Transaction
    │
    ├── Attempt 1
    ├── Attempt 2
    └── Attempt 3
```

This one-to-many relationship is an important part of the FinLeak data model.
