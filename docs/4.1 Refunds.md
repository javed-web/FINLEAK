# 💰 Stage 4.1 — Refunds

## 🎯 Objective

The next layer in FinLeak is to model **customer refunds**.

Refunds are important because a transaction can initially appear successful and generate revenue, but later some or all of that transaction value can be returned to the customer.

The goal was to create realistic refund data that can later be used to answer questions such as:

- How much transaction value was refunded?
- Which merchants have unusually high refund activity?
- Which categories generate the most refunds?
- Are certain refund reasons more common?
- Are refund patterns concentrated in particular periods?
- How much money is actually refunded versus still pending?

---

## 💡 Refund Design

Refunds were generated only for transactions whose original status was:

```text
SUCCESS
```

The target refund rate was approximately:

```text
5% of successful transactions
```

### Refund rules

| Attribute | Design |
|---|---|
| Eligible transactions | Successful transactions |
| Target refund rate | ~5% |
| Full refunds | 60% |
| Partial refunds | 40% |
| Partial refund amount | 10%–90% of transaction amount |
| Refund delay | 1–15 days |
| COMPLETED | 90% |
| PENDING | 7% |
| FAILED | 3% |

### Refund reasons

The generator uses six possible reasons:

```text
CUSTOMER_REQUEST
ORDER_CANCELLED
DUPLICATE_PAYMENT
PRODUCT_NOT_RECEIVED
SERVICE_ISSUE
PRODUCT_ISSUE
```

---

## 🗄️ Database

Refunds are stored in the existing `refunds` table.

```sql
CREATE TABLE refunds (
    refund_id VARCHAR(30) PRIMARY KEY,
    transaction_id VARCHAR(30) NOT NULL,
    refund_timestamp DATETIME NOT NULL,
    refund_amount DECIMAL(15,2) NOT NULL,
    refund_reason VARCHAR(100),
    refund_status VARCHAR(30) NOT NULL,

    FOREIGN KEY (transaction_id)
        REFERENCES transactions(transaction_id)
);
```

The `transaction_id` links every refund back to its original transaction.

This allows us to compare:

```text
Transaction Amount
        ↓
Refund Amount
        ↓
Remaining Transaction Value
```

---

## 🧠 Generation Logic

The refund generator was implemented in:

```text
python/generate_refunds.py
```

The process was:

1. Select successful transactions.
2. Apply the ~5% refund rate.
3. Decide whether the refund is full or partial.
4. Generate the refund amount.
5. Generate a refund date between 1 and 15 days after the transaction.
6. Assign a refund status.
7. Assign a refund reason.
8. Insert the records into MySQL in batches.

The generator uses a fixed random seed so that the dataset remains reproducible.

## 🧪 Validation

After generation, the refund data was validated against the transaction table.

### 1. Refund count

Confirmed that the expected number of refund records were created.

### 2. Transaction eligibility

Every refund was checked to ensure its original transaction had:

```text
transaction_status = SUCCESS
```

No invalid refund-to-failed-transaction relationships were found.

### 3. Refund amount

Each refund was checked to ensure:

```text
refund_amount > 0
```

and:

```text
refund_amount <= transaction.amount
```

No invalid refund amounts were found.

### 4. Refund timing

Every refund was checked to ensure that:

```text
refund_timestamp > transaction_timestamp
```

The generated refund window was also confirmed to be within:

```text
1–15 days
```

### 5. Duplicate refunds

Transactions were checked for multiple refund records.

No duplicate refund relationships were found.

### 6. Refund statuses

The generated statuses were checked to ensure that the configured statuses were represented and that `COMPLETED` was the dominant status.

## 🧩 Important Financial Modeling Decision

Not every refund record represents money that has actually left PayFlow.

A refund can have one of three states:

```text
COMPLETED
PENDING
FAILED
```

Therefore, later financial calculations will treat them differently.

### Actual refunded value

Only:

```text
refund_status = 'COMPLETED'
```

will be counted as realized refunded money.

### Pending exposure

```text
refund_status = 'PENDING'
```

will be tracked separately because the money may still be refunded.

### Failed refunds

```text
refund_status = 'FAILED'
```

will not be counted as actual refunded value.

This distinction will become important when calculating **net financial contribution** later in the project.
