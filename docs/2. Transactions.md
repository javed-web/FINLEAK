# Stage B — Transactions 💳

> **Status:** 🔒 Completed & Validated

---

## 🎯 Objective

After completing the customer and merchant layer, the next step was to generate the actual payment activity.

For this stage, I generated **1,000,000 transactions** covering the period from January 2025 to June 2026.

The transaction table is the central table in FinLeak because the other payment-related tables will eventually connect back to it.

The goal wasn't just to create one million random transactions.

I wanted the data to have:

- Different payment methods
- Multiple payment gateways
- Different transaction channels
- Successful and failed transactions
- Different transaction amounts
- Realistic time distribution
- Failure reasons
- A controlled anomaly that can be discovered later through analysis

---

## 🗄️ Transaction Table

The table is:

```text id="n0d3xp"
transactions
```

The main columns are:

| Column | Description |
|---|---|
| `transaction_id` | Unique transaction identifier |
| `customer_id` | Customer associated with the transaction |
| `merchant_id` | Merchant receiving the payment |
| `transaction_timestamp` | Date and time of transaction |
| `amount` | Transaction amount in INR |
| `payment_method` | Method used for payment |
| `gateway` | Payment gateway used |
| `transaction_status` | SUCCESS / FAILED |
| `failure_reason` | Reason for failed transaction |
| `currency` | Transaction currency |
| `channel` | Transaction channel |

The table also has foreign-key relationships with the customer and merchant tables.

# 💰 Transaction Amount Generation

Transaction amounts were generated using a log-normal distribution.

I used this instead of a uniform random distribution because transaction amounts in a payment system are unlikely to be evenly distributed.

The generated amounts were constrained between:

**₹50 → ₹100,000**

This prevents unrealistic values such as extremely small or extremely large transactions from dominating the dataset.

The resulting data contains a mix of lower-value and higher-value transactions.

That variation will become useful later when investigating whether financial leakage is concentrated among high-value transactions.

# 🐛 Problem Encountered During Data Loading

The first 10,000-transaction version of the generator exposed an issue while inserting the data into MySQL.

Some successful transactions had `NULL` in the `failure_reason` field.

When the data was passed through Pandas, these values became `NaN`.

MySQL did not accept the Pandas `NaN` value in the way the insert operation expected.

The insert therefore failed.

I fixed this by converting Pandas missing values back to Python `None` before sending the rows to MySQL.

The relevant transformation was:

```python
rows = [
    tuple(None if pd.isna(value) else value for value in row)
    for row in rows
]
```

After applying the fix, the transaction data loaded successfully.

I then cleared the test transaction data and regenerated the final **1,000,000-row dataset**.

This was one reason I decided to validate each stage before moving to the next one.

# ⚙️ Generation Approach

The initial version generated transactions using a Pandas DataFrame.

That worked for a smaller test dataset, but generating one million transactions as a single large DataFrame wasn't the approach I wanted for the final pipeline.

For the final version, I changed the generator to process transactions in batches.

The final approach was:

```text id="d6q5n9"
Generate batch
     ↓
Prepare rows
     ↓
Convert missing values
     ↓
Insert into MySQL
     ↓
Generate next batch
     ↓
Repeat until 1,000,000
```

The final generator processes transactions in batches of **25,000**.

This keeps memory usage under control and allows the data to be loaded directly into MySQL.

# 🔗 Why This Table Matters

The transaction table is the point where the customer and merchant layers become actual business activity.

The relationship is:

```text id="1h3t4f"
Customer
   │
   └── Transaction
          │
          ├── Gateway
          ├── Payment Method
          ├── Channel
          ├── Amount
          ├── Status
          └── Failure Reason
```

The next tables will extend this transaction record.

For example:

```text id="0qk8z4"
Transaction
   │
   ├── Payment Attempts
   ├── Refunds
   ├── Chargebacks
   └── Fees
```

This is what will eventually allow me to calculate the actual financial impact of operational problems.

# 📈 Early Signal

The Gateway_A incident was intentionally designed as an early test case for the later investigation pipeline.

The transaction layer establishes the incident period, while the payment-attempt layer gives us a more detailed view of what happened during individual payment attempts.

After the payment-attempt data was generated, the incident showed a much stronger signal:

| Period | Attempts | Failed Attempts | Failure Rate |
|---|---:|---:|---:|
| Outside Incident | 311,040 | 22,655 | 7.28% |
| Incident | 1,493 | 335 | **22.44%** |

The incident-period payment-attempt failure rate is approximately **3.1×** the outside-incident rate.

This is the type of signal I want the later investigation engine to identify automatically.
